# گزارش ساختار Prooflane برای رقابت‌سنجی

تاریخ تهیهٔ فایل: ۹ نوامبر ۲۰۲۶  
مبنای وضعیت: گزارش بررسی‌شده در گفت‌وگوی قبلی، ۸ نوامبر ۲۰۲۶. برای ساخت این فایل تست یا بررسی تازه‌ای اجرا نشده است.

هدف: ارزیابی رقابتی بر اساس پیاده‌سازی واقعی، نه صرفاً ایده یا ظاهر.

## ۱. تعریف محصول

Prooflane زیرساخت اجرای کار وابسته و تسویهٔ مشروط برای عامل‌های AI است.

مشتری یک توافق ثابت برای چند وظیفه ایجاد می‌کند. وظیفهٔ دوم باید خروجی پذیرفته‌شدهٔ وظیفهٔ اول را مصرف کند. خروجی‌ها با قواعد مشخص بررسی می‌شوند و تنها پس از پذیرش همهٔ وظایف لازم، قرارداد NEAR سهم عامل‌ها را قابل برداشت می‌کند.

ارزش اصلی: اتصال «توافق → اجرای وابسته → شواهد بررسی → تخصیص وجه» در یک جریان قابل پیگیری.

## ۲. سناریوی MVP

سناریوی فعلی، مقایسهٔ پیشنهادهای تأمین‌کنندگان است:

1. **Extract & Cite:** استخراج قیمت، تعداد، هزینهٔ ارسال، زمان تحویل و ارجاع از منابع ثابت.
2. **Compare & Select:** مصرف خروجی پذیرفته‌شدهٔ مرحلهٔ اول و انتخاب پیشنهاد واجد شرایط بر اساس بودجه و زمان تحویل.
3. **Verification:** تولید گزارش شامل نتیجهٔ هر بررسی، انتظار، واقعیت و دلیل.
4. **Settlement:** ثبت نتایج توسط بررسی‌کنندهٔ تعیین‌شده و تخصیص سهم‌ها پس از پذیرش کامل.

بودجهٔ خرید کالا با حق‌الزحمهٔ عامل‌ها در NEAR دو مقدار مستقل‌اند. MVP خرید واقعی از تأمین‌کننده انجام نمی‌دهد.

## ۳. ساختار فنی

| لایه | پیاده‌سازی فعلی |
| --- | --- |
| منطق مرکزی | TypeScript؛ توافق، قواعد دامنه، بررسی و ماشین حالت |
| قرارداد | Rust و near-sdk؛ اسکرو با native NEAR |
| ذخیره‌سازی | SQLite برای اجرای قابل بازتولید؛ PostgreSQL/Supabase برای محیط توسعه |
| شواهد | آرشیو خصوصی خروجی‌ها و گزارش‌ها با هش |
| اجرای پس‌زمینه | صف کار، lease، fencing و بازیابی اجرای نیمه‌تمام |
| ورود | امضای پیام کیف پول Testnet و نشست سمت سرور |
| رابط | HTML/CSS/JavaScript؛ Overview، Orders، Workflow و Evidence |
| اتصال مدل | آداپتور و runner برای NEAR AI Cloud؛ اجرای زنده هنوز تأیید نشده |

## ۴. تضمین‌های اصلی طراحی

- توافق، منابع، سیاست بررسی، وابستگی‌ها و سهم‌ها پیش از تأمین وجه ثابت می‌شوند.
- خروجی هر مرحله نسخه و هش مشخص دارد.
- مقایسه به هش دقیق خروجی پذیرفته‌شدهٔ استخراج وابسته است.
- قواعد بررسی از داده و سیاست ثابت‌شده خوانده می‌شوند.
- مدل نمی‌تواند گیرندهٔ پول، سهم‌ها یا تصمیم نهایی پرداخت را تعیین کند.
- ذخیرهٔ وضعیت، خروجی، گزارش و رویدادها به‌صورت اتمیک انجام می‌شود.
- درخواست تکراری نباید خروجی، گزارش یا رویداد تکراری بسازد.

این موارد باید با توجه به مرز اعتماد بررسی‌کننده و تفاوت سورس فعلی با قرارداد تاریخی مستقرشده خوانده شوند.

## ۵. بررسی خروجی‌ها

بررسی فعلی deterministic و محدود به سناریوی تعریف‌شده است:

- اعتبار ساختار و هویت خروجی.
- تطبیق اطلاعات عددی با قالب ساختاریافتهٔ منابع نمونه.
- پوشش منابع و وجود ارجاع.
- صحت محاسبهٔ هزینه.
- رعایت بودجه، تعداد و ارز.
- بررسی شرایط تحویل؛ زمان نامعلوم، واجد شرایط بودن را اثبات نمی‌کند.
- تطبیق هش وابستگی و جلوگیری از تغییر اطلاعات پذیرفته‌شده در مرحلهٔ مقایسه.

خروجی نامعتبر می‌تواند به اصلاح نیاز داشته باشد؛ سقف اصلاح محدود است. شکست نهایی، ادامهٔ مسیر موفق را مسدود می‌کند.

محدودیت: سیستم هنوز صحت معنایی اسناد آزاد یا حقیقت اطلاعات دنیای بیرونی را اثبات نمی‌کند.

## ۶. مدل مالی و نقش واقعی NEAR

- وجه در قرارداد اسکرو نگهداری می‌شود.
- پذیرش نتایج روی زنجیره توسط یک بررسی‌کنندهٔ مشخص و مورد اعتماد ثبت می‌شود.
- تخصیص سهم‌ها فقط پس از پذیرش تمام وظایف لازم انجام می‌شود.
- پذیرش یک مرحله به‌تنهایی پرداخت جزئی ایجاد نمی‌کند.
- نهایی‌سازی موفق، اعتبار قابل برداشت ایجاد می‌کند؛ برداشت عملیات جداگانه است.
- شکست نهایی یا انقضای واجد شرایط، مسیر بازپرداخت کامل مشتری را دارد.
- اعتبار موفق و بازپرداخت یک اصل وجه، نباید هم‌زمان امکان‌پذیر باشند.
- انتقال‌های غیرهم‌زمان با وضعیت pending و callback مدیریت می‌شوند.

مرز اعتماد: اجرای بررسی خارج از زنجیره است. قرارداد، اجرای غیرمتمرکز بررسی یا داوری AI را اثبات نمی‌کند. بررسی‌کنندهٔ مخرب همچنان یک ریسک اعتماد است.

## ۷. شواهد اجرای واقعی

مسیرهای تاریخی Testnet در پروژه ثبت شده‌اند:

- سفارش موفق: ثبت نتایج، تخصیص سهم و برداشت واقعی test NEAR.
- سفارش منقضی: بازپرداخت کامل اصل وجه.

قرارداد تاریخی روی `arlos.testnet` است. شناسهٔ سفارش‌ها و تراکنش برداشت در صفحهٔ دمو و README درج شده‌اند.

در دموی تاریخی، یک حساب برای بررسی و دریافت سهم هر دو عامل استفاده شده است؛ این دمو استقلال اقتصادی چند عامل را نشان نمی‌دهد.

نسخهٔ سخت‌سازی‌شدهٔ جدید قرارداد در سورس محلی وجود دارد، اما هنوز روی حساب تاریخی Testnet مستقر نشده است.

## ۸. امنیت

کنترل‌های پیاده‌شده:

- بررسی مجدد اعتبار کلید کیف پول پیش از درخواست‌های تغییردهنده.
- محدودیت عمر و بی‌کاری نشست و اتصال نشست به مبدأ ورود.
- محدودیت درخواست، اندازهٔ ورودی و پاسخ‌های RPC.
- رد JSON مبهم، کلیدهای تکراری و UTF-8 نامعتبر.
- کنترل هش و آرشیو خصوصی شواهد.
- بازاجرای بررسی deterministic روی زنجیرهٔ وابستگی شواهد، پیش از آماده‌سازی verdict جدید.
- محافظت از callbackها و حسابداری انتقال‌های pending در قرارداد.

این موارد ممیزی مستقل، گواهی امنیت یا آمادگی برای نگهداری پول واقعی نیستند. بررسی مجدد شواهد در برنامه انجام می‌شود، نه داخل قرارداد.

## ۹. تست و بازتولید

آخرین اجرای ثبت‌شدهٔ مجموعهٔ اصلی در زمان گزارش:

- ۸۰ تست برنامه پاس شده است.
- بررسی TypeScript و syntax پاس شده است.
- تست‌های قرارداد و انتقال‌های واقعی Sandbox در مراحل قبلی اجرا شده‌اند؛ این گزارش آن‌ها را دوباره اجرا نکرده است.
- جریان دو وظیفه تا تولید دو گزارش، فیلتر سفارش‌ها و بازخوانی داده در مرورگر آزمایش شده‌اند.

اجرای محلی بدون کلید مدل یا سرویس دیتابیس خارجی:

```bash
npm run dev:console
npm run demo:verification
npm test
```

README مسیر «دستور را اجرا کن → این نتیجه را ببین» دارد.

## ۱۰. وضعیت فرانت‌اند

- **Overview:** آمار واقعی سفارش‌های بارگذاری‌شده و ورود به فهرست مرتبط.
- **Orders:** جست‌وجو، فیلتر و انتخاب سفارش.
- **Workflow:** ایجاد سفارش، انتخاب وظیفه، ورود دستی/نمونه، بررسی خروجی و عملیات مالی مشروط.
- **Evidence:** گزارش‌ها، هش‌ها، دلایل بررسی، رویدادها و تراکنش‌های دیتابیس.

رابط انگلیسی، شیشه‌ای و دارای بک‌گراند موجی زنده است. تست نهایی موبایل، تمام حالت‌های خطا و مسیرهای مالی با کیف پول مالک هنوز نیازمند تکمیل است.

## ۱۱. موارد ناتمام یا تأییدنشده

- اجرای زندهٔ عامل‌ها با API واقعی.
- کیفیت و پایداری خروجی مدل واقعی.
- انتخاب و تأیید ارائه‌دهندگان رایگان مطابق خواستهٔ مالک؛ آداپتور فعلی NEAR AI Cloud به‌تنهایی این الزام را تأمین نمی‌کند.
- اتصال تجربهٔ اجرای زندهٔ مدل به رابط.
- استقرار نسخهٔ جدید قرارداد و اعتبارسنجی مجدد آن.
- تثبیت نهایی فرانت‌اند و دمو.
- عمومی‌بودن ریپو، انتشار دمو و تکمیل سابمیشن باید جداگانه تأیید شوند.

در وضعیت فعلی، نباید پروژه را «کسب‌وکار کاملاً خودمختار با AI زنده» معرفی کرد.

## ۱۲. فرضیهٔ تمایز رقابتی

- وابستگی واقعی خروجی‌ها، فراتر از یک سقف خرج یا allowlist.
- توافق ثابت و اتصال گزارش‌ها به همان توافق.
- گزارش قابل توضیح به‌جای verdict مبهم.
- تسویهٔ کامل مشروط به موفقیت جریان وابسته.
- مسیر شکست و بازپرداخت قابل نمایش.
- اجرای محلی قابل بازتولید بدون API پولی.

این‌ها فرضیه‌های تمایز هستند؛ برتری نسبت به رقبا بدون بررسی کد و دموی آن‌ها اثبات نشده است.

## ۱۳. درخواست از ایجنت رقابت‌سنجی

رقبا را بر اساس ریپو، دمو و شواهد واقعی مقایسه کن و مشخص کن:

1. کدام پروژه‌ها همین جریان وابسته و تسویهٔ مشروط را واقعاً اجرا کرده‌اند؟
2. نقش NEAR در هر پروژه چقدر ضروری است؟
3. مرز اعتماد بررسی‌کننده و امنیت وجوه چگونه مدیریت می‌شود؟
4. دموی آن‌ها چقدر قابل بازتولید و قابل فهم است؟
5. نبود اجرای زندهٔ مدل و عدم استقلال عامل‌ها چقدر ما را عقب می‌اندازد؟
6. سه تغییر کم‌هزینه با بیشترین اثر رقابتی چیست؟

برای رتبه یا درصد برتر بودن، عدد قطعی تولید نکن. اگر تخمین ارائه می‌کنی، مجموعهٔ رقبا، شواهد، فرض‌ها و سطح اطمینان را مشخص کن. آمار و مقررات هکاتون نیز باید از منابع رسمیِ روز بررسی شوند.

هدف ارزیابی: تقویت همین محصول با حفظ دامنهٔ MVP؛ نه افزودن فناوری یا بازطراحی صرفاً برای پیچیده‌ترشدن.
